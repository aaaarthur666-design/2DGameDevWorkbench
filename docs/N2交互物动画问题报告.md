# N2 前置小测问题报告：交互物状态过渡为什么失效

2026-11-10 · `paper-vbyc` · 小测版本 `69a1587`

**决定：结束本轮小测，N2 暂缓。** 8 条真实 PixelLab 动画全部生成完成，只有 1 条同时满足目标状态、过渡连贯和固定部件保持三项要求。Forge 若要支持交互物状态链，需要能判断一段动画是否按指定方式运动、是否停在可复用的状态，以及哪些本应保留的内容发生了变化。N2 负责把物品原图移送为动画参考，开放这一入口本身不会改善上述行为。

## 小测实际覆盖了什么

4 种交互物各使用一张已选定的 128×128 透明 PixelLab 原图。同一物品的两次请求使用相同 A 图、相同动作文字，种子分别为 1101、2202。直接调用 `animate-with-text-v3`，只提供首帧条件。每次请求 16 帧，均返回 17 张图，返回的第一张与输入 A 图可见像素一致。下文帧号从 1 开始，包含这张首帧。

判定依据是主评 Agent 对完整序列和实际末帧的检查，辅以像素记录。原定进入条件为至少 3 种物品各有一条通过，且至少 2 种在两个种子下都通过。实际分别是 **1 种和 0 种**。两条拉杆序列都缺少合格中位末帧，因此没有执行第二段接续。

## 故障证据与影响

| 对象与预期行为 | 两个种子的实测结果 | 对工具的要求 |
| --- | --- | --- |
| 宝箱。仅箱盖绕铰链翻到完全打开，前扣留在箱身 | **0/2。** 两次都露出了空箱，箱脚稳定，但前扣随盖子翻起，末帧只部分打开。原图上的金扣横跨箱盖与箱身，部件归属也有视觉歧义。 | “箱子打开了”不足以判定成功。系统需要知道哪个部件运动、哪个部件固定，以及打开到什么程度才算完成。 |
| 拉杆。从左档转到竖直中位并停住 | **0/2。** 两次都在第 3 帧经过近竖直位置，随后越过中位，最终停在左侧。底座保持稳定。制作 A 图时，第一张原图就处在中位，筛除后补生成了左倾图。 | 输入状态、经过目标姿势、稳定结束是三个独立判断。直接把最后一帧当成 B 会存入错误档位，只要中途出现过目标就判通过也会误判。 |
| 栅门。刚性栅条垂直升起，停在半开位置 | **0/2。** 石框稳定，两条序列的栅条却都倾斜翻动；2202 的栅条在末段穿出顶部石梁。 | 通道变宽只能说明发生了变化。判定升降还需要看运动方向、部件朝向和遮挡关系。错误轨迹即使抵达近似高度，也不能交付为升降过渡。 |
| 指示灯。灯面从灰暗过渡到持续绿色，灯壳固定 | **1/2。** 2202 的过渡和末帧可用。1101 的末帧同样可用，但第 7 帧灯面中央 25×28 区域的 700 个像素全部透明，第 6、8 帧该区域均为不透明。 | 状态图与过渡动画应分别给出结论。仅检查首末帧会放过一次明显闪空，仅给整条动画一个失败标签又会丢失末帧可用的信息。 |

## 能够归因到哪一层

**生成器。** 动作文字已经写明了铰链、固定面板、终点停留、垂直平移和持续亮绿等要求。当前调用把这些要求作为文本提交给 PixelLab，首图、帧数、透明背景和种子作为独立参数。观察到的事实是，返回序列多次违背了文字中明确的约束。单张参考图、投影视角和生成器行为各自贡献了多少，现有数据无法区分。适配器支持可选末帧图，本轮没有使用，因此也没有证据说明加入 B 图可以纠正中间轨迹。[PixelLab 适配器](../Tools/SpritePipeline/sprite_pipeline/providers/pixellab.py)

**Forge。** N1 已支持交互物身份，物品原图的正式移送入口仍关闭。这次直接检查供应商返回的候选，没有经过完整的 Forge 规划、分段复核、人工采用和写回流程。因此可以把这些缺陷列为交互物工具必须处理的输入，不能据此认定现有复核器错误放行了 7 条动画。角色流程已有真实锚点选择、截尾确认和复核记录，这些能力可以复用；交互物仍缺少能描述部件、运动轨迹和终态的专用合同，以及把核准结果登记为状态的流程。[移送实现](../lib/workbench/adapters/reference-art.mjs) · [现有锚点与复核](sprite-generator.md) · [N2–N6 的职责](论文分支执行计划.md)

**实验结论。** 这是一轮工程可行性观察，每种物品只有一张选定原图和两个种子，结果由一个 Agent 评定。1/8 是这批原始候选的通过数，不能外推为 PixelLab 对所有交互物的成功率。它足以支撑当前分支的暂停决定，也说明后续工程需要解决哪些重复出现的错误。截短、补帧或手工调整某个样本属于另一种处理条件，无法证明原工具已经具备通用能力。

## 应修到工具里的能力

| 优先顺序 | 工程改进 | 可供开发和评审使用的完成标准 |
| --- | --- | --- |
| 1. 让任务规格可以检查 | 在交互物合同中记录 A、B 状态、运动部件、固定部件、允许的运动方式、终点和停留要求。固定区域与可遮挡区域分别描述。生成前将 A 的要求与实际参考图核对，歧义允许人工标明。 | 规划、提交和复核共用同一份要求。使用者能在生成前看到哪些条件可以直接施加，哪些只能在结果中检查。 |
| 2. 给出有证据的质量结论 | 分别记录“B 状态图可用”“整段过渡可用”“固定内容保持”。对指定区域比较轮廓、部件位置、运动方向和逐帧 Alpha。已有相邻帧变化指标可作线索；合法遮挡、发光或有意停顿仍按任务语义判断。 | 每项缺陷能定位到帧、区域和被违反的要求。证据不足可交由人工判断。即使末帧合格，过渡缺陷仍随候选保留。[现有相邻帧测量](../Tools/SpritePipeline/sprite_pipeline/collaboration/motion_evidence.py) |
| 3. 把状态采用与下一段输入明确绑定 | 复用现有检查点，分别记录目标首次到达、持续时长和最终停留。由评审确认可采用的真实状态帧、对应过渡范围和来源。任何裁剪或修正保留独立版本与理由。 | 下游能追溯 B 来自哪个候选、哪一帧、哪次裁决；只有获得相应确认的产物才能用于接续或作为已通过的过渡交付。[检查点实现](../Tools/SpritePipeline/sprite_pipeline/collaboration/checkpoints.py) |
| 4. 给硬性运动要求选择可控的实现 | 当任务要求刚体平移、绕固定轴旋转或严格保护某个区域时，可设计部件分层、轴点变换、受限区域合成等通用能力。它们依赖清楚的部件边界、轴点和遮挡关系；开盖后新露出的内部也需要可用像素。输入不足时应显示限制。 | 同一种运动方式能用于不同物品。工具记录实际采用的是模型生成、确定性变换还是组合方法，便于评估各自的适用范围。此项属于设计建议，现有样本尚未验证修复效果。 |

**工程取舍。** 优先明确交互物合同和采用规则，再决定哪些视觉要求值得做成可控操作。检查可以阻止错误状态进入下一段；提高产出合格候选的能力还需要对生成或合成过程施加实际约束。论文目前可以报告上述失效类型和工具边界，交互物状态链的有效性仍是未证实的主张。角色长动作主实验有独立的证据与计划。

## 费用与证据位置

共生成 5 张原图（含 1 张筛除的拉杆原图）和 8 条动画，分别计 5 和 32 个试用单位。账户从 40 降至 3，实际美元扣款为 0。按方案中的估算单价折算为 US$0.3816，授权上限为 US$0.75。

仓库中的[小测样例](../examples/n2-pilot-20261110/)包含 4 种物品的实际起始图、8 条完整序列和筛除的第一张拉杆图。每个物品的 `reference-input.json` 记录选定原图的实际生成参数，两个种子目录各含 17 张原始 PNG 和逐帧测量。可从[同步预览](../examples/n2-pilot-20261110/first-round.gif)查看动作，结合[预定方案](../examples/n2-pilot-20261110/protocol.json)和[逐条裁决](../examples/n2-pilot-20261110/run-summary.json)核对结论。原始服务回执保存在本地 `outputs/n2-pilot-20261110/`。
