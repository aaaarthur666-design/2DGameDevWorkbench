## 0. 文档用途与事实边界

本文定义一个独立于 CopyWorms 的可玩小游戏，用于验证和展示 Forge 从资产生产、人工编辑、资源导出到 WorkBuddy 工程接入的完整流程。

本次交付仅为策划文档。未创建游戏工程、生成美术、调用付费模型或执行游戏验收。下文的脚本名、设计 ID、参数、目录、任务和测试用例均为实施约定；只有明确标注“现有”的部分代表已核对的工作台能力。

## 1. 项目定义

### 1.1 一句话概念

暴风雨后的港口失去航标。玩家扮演最后一名值守维修员，在一座停电的灯塔站寻找备用电池、接通线路，重新点亮指引归航的灯。

### 1.2 产品目标

| 维度 | 设计目标 | 验收依据 |
| --- | --- | --- |
| 游戏闭环 | 从开始界面进入，经移动、探索、交互，完成点灯并重新开始 | 完整通关及重开录像 |
| 上手成本 | 玩家只需左右移动、跳跃和交互，无教程阅读负担 | 首次体验者能够独立识别目标 |
| 情绪表达 | 从冷清停电到温暖恢复，形成可见、可听的反馈 | 前后状态对比及实际演出 |
| 工作台价值 | 同一作品真实使用角色、地图、交互物和工程接入流程 | 资产来源与工程资源对应记录 |
| 可修改性 | 电池需求数量由统一配置驱动，规则和文字同步变化 | 两块改一块的实际回归 |
| 可交接性 | 换一位成员能根据文档定位资源、继续制作并复现验收 | 干净目录交接检查 |

### 1.3 基本规格

| 项目 | v1.0 约定 |
| --- | --- |
| 类型 | 横版探索与轻机关修复；不以高难跳跃或复杂推理为核心 |
| 视角 | 正交侧视 2D；固定高度的横向跟随镜头 |
| 玩家数 | 单人、离线 |
| 引擎 | Godot 4.6.x；实施时冻结完整补丁版本及导出模板版本 |
| 首发体验平台 | Windows 桌面、键盘；其他平台单独验证后再声明支持 |
| 基础画面 | 640 × 360 逻辑画面，默认 1280 × 720 窗口；支持常见 16:9 显示 |
| 关卡规模 | 一张连续地图，约三个屏幕宽，三个功能区域 |
| 目标时长 | 首次体验约 2–4 分钟，熟悉后约 60–90 秒；属于待实测目标 |
| 文本语言 | 简体中文；工程 ID 使用英文 |
| 失败与惩罚 | 无生命值、敌人或计时失败；越界提供无损恢复 |
| 存档 | 不保存局内进度；每次“重新开始”建立全新一局 |
| 游戏运行依赖 | 成品游戏无需 WorkBuddy、API Key、浏览器、Node 或 Python 在线运行 |

### 1.4 设计支柱

1. **一眼看见目标。** 出生区域通过方向标识与 HUD 明确灯塔位置；进入中央区后直接看到未亮的灯塔。
2. **每次操作都有反馈。** 拾取改变计数和物件状态；开关改变线路状态；点灯改变整个场景气氛。
3. **允许不同探索顺序。** 可以先开线路或先找电池；可以提前查看终端，不会进入死局。
4. **完成之后仍可修改。** 美术来源、运行规则、文字和导出包彼此可追溯，配置修改无需重做全套资产。

## 3. 世界观、角色与叙事

### 3.1 场景背景

一场暴风雨导致港口照明中断，灯塔的常规供电失效。备用电池散落在维修站两侧，线路隔离开关仍处于关闭状态。维修员需要恢复最后一盏航标灯。

不展开人物身世、世界年表和对白树。信息通过环境、维修提示、状态反馈和结尾完成。

### 3.2 主角

- 身份：灯塔站维修员；工作名“守灯人”，不设正式姓名。
- 轮廓：短外套、工具腰包、明确的头部防护轮廓；不携带长武器或复杂飘带。
- 色彩：深蓝工作服，少量暖黄色识别块。
- 动作：克制、清晰、重心稳定；交互时保持站立动画，不额外制作伸手动画。
- 朝向：角色源图统一朝右，运行时只水平翻转视觉节点。

### 3.3 叙事信息分配

| 载体 | 作用 | 内容边界 |
| --- | --- | --- |
| 开始界面副标题 | 给出情境 | “找到备用电池，让港口重新看见光。” |
| 维修提示牌 | 告诉玩家步骤 | 找电池、接线路、回终端启动 |
| 终端反馈 | 指出当前缺项 | 缺电池、线路未接通或准备完成 |
| 点灯演出 | 兑现目标 | 指示灯、光束、环境亮度和声音变化 |
| 胜利界面 | 给出结束 | “最后一盏灯，亮了。” |

## 4. 玩法规则与状态

### 4.1 操作表

| 输入 | 游玩时 | UI / 对话时 |
| --- | --- | --- |
| A / D 或左右方向键 | 水平移动 | 菜单焦点操作按实际 UI 实现 |
| Space | 地面起跳，空中不连续起跳 | 对话显示期间不触发跳跃 |
| E | 与最近的合格物件交互 | 补全当前文字，再推进或关闭当前页 |
| Enter | 不作为第二套世界交互键 | 开始 / 确认；对话中沿用现有 `ui_accept` 推进 |
| Esc | 空闲游玩时打开或关闭暂停菜单 | 交互对话和点灯演出期间不另开暂停层 |
| 鼠标 | 不用于场景交互 | 点击菜单、下一页或完成按钮 |

所有世界物件统一使用 `proximity_press` 与 `workbench_interact`，默认 E。禁止同时再给 E 注册一套独立物件扫描逻辑。

同一次按键只能被一个上下文消费：菜单 / 对话优先，其次当前物件。按住 E 的自动重复不算新的一次交互。

### 4.2 唯一规则数据

`DemoConfig` 是以下可调规则的唯一来源；`DemoRunState` 是局内状态的唯一来源。两者均为本 Demo 计划新增，不是 Forge 现有对象。

| 字段 | 类型 / 初值 | 语义 |
| --- | --- | --- |
| `required_cells` | 整数，2 | 点灯所需的不同电池实例数量；v1.0 只允许 1 或 2 |
| `available_cell_ids` | 两个稳定实例 ID | 本关可以计入修复条件的电池白名单 |
| `run_id` | 每局唯一值 | 区分重开前后的异步事件 |
| `collected_cell_ids` | 空集合 | 已拾取电池；禁止用重复事件累加整数 |
| `line_enabled` | false | 当前线路开关的真实开关值 |
| `phase` | 初始化后 PLAYING | 见下方阶段表 |
| `paused` | false | 只允许在 PLAYING 且交互空闲时改变 |

派生条件：

```text
collected_total = 有效 collected_cell_ids 的数量
cells_ready = collected_total >= required_cells
can_start = phase == PLAYING 且非 paused 且 cells_ready 且 line_enabled
```

配置加载时必须拒绝：需求小于 1、需求大于可用唯一电池数、重复实例 ID、找不到配置指定物件、未识别的模板占位符。不得把无效配置静默改为默认值后继续发布。

### 4.3 阶段表

| 当前阶段 | 允许的变化 | 禁止的行为 |
| --- | --- | --- |
| INITIALIZING | 校验配置、挂载场景、绑定对象、同步 UI，完成后进入 PLAYING | 接受玩家交互、显示可开始但资源未就绪的状态 |
| PLAYING | 移动、收集、切换、检查终端；满足条件可进入 LIGHTING | 重复计数；未满足条件直接点灯 |
| LIGHTING | 锁定本次成功、播放演出，结束后进入 WON | 再次点灯、关掉线路、打开暂停菜单 |
| WON | 显示结果，接受重新开始或退出 | 再消费旧物件事件或改变通关结论 |
| RESTARTING | 卸载旧关卡，建立新 run_id 并重新初始化 | 旧计时器、旧信号修改新一局 |

`paused` 不改变修复进度。电池和开关操作都发生在 PLAYING；点灯前开关可反复切换，点灯后进入锁定结果，不再恢复停电。

### 4.4 终端判定表

| 电池满足 | 线路开启 | 按 E 的结果 |
| --- | --- | --- |
| 否 | 否 | 提示缺少电池，并提示线路未接通 |
| 否 | 是 | 提示还缺几块电池 |
| 是 | 否 | 提示前往右侧接通线路 |
| 是 | 是 | 进入 LIGHTING，开始唯一一次点灯 |

进入终端范围只显示交互提示，不自动通关。收齐最后一块电池或打开开关也不自动点灯，必须回到终端明确操作。

电池不在中途消耗。允许先开线路、后收电池，也允许先收电池、后开线路。需求改成 1 后，两块电池仍都可拾取；条件使用大于等于，第二块不影响通关。

### 4.5 拾取、反馈与异常恢复

- 电池拾取成功后隐藏，取消时保留；只在 `picked_up` 成功信号中登记。
- 用实例 ID 去重；共享同一电池外观不意味着共享拾取状态。
- 电池 HUD 显示 `min(collected_total, required_cells) / required_cells`；满足时显示“备用电池已齐”。
- 开关使用最新 `toggleState`，不靠收到事件后自行取反。
- 终端失败只显示非阻塞状态提示，停留约 2.5 秒；不会扣资源或锁住玩家。
- 开关和电池的重复失败操作不会刷屏或重复播放成功音效。
- 正常关卡不包含致死坑。若因碰撞缺陷跌出有效范围，恢复到最近安全地面点、清零速度并保留进度；该恢复不能掩盖发布前必须修复的可复现碰撞错误。

### 4.6 重开与退出

重开入口仅放在暂停菜单和胜利界面。重开必须同时重置电池可见性、已收集集合、开关、目标文案、灯塔外观、音频、角色位置、镜头、输入锁与交互状态。正常重开通过卸载和重建整关完成，不逐个猜测并修改遗留状态。

本关交互物记忆统一使用 `instance`。不启用 `session` / `persistent`，不把工作台生产记录或浏览器草稿当成游戏存档。

## 5. 关卡设计

### 5.1 空间结构

设计坐标采用 Godot 逻辑像素，X 向右、Y 向下。设计区域约为 `[0,1920] × [0,360]`，主地面脚底 Y 为 304。地图最终尺寸以人工编辑后的导出为准；如需调整整体布局，应同步登记坐标变换，不能只移动底图。

| 区域 | X 范围 | 功能与内容 | 希望形成的体验 |
| --- | --- | --- | --- |
| A：维修入口 | 0–640 | 出生点、提示牌、电池 A、灯塔方向标识 | 学会移动与 E，完成第一次拾取 |
| B：灯塔控制区 | 640–1280 | 灯塔主体、中央终端、清晰回程路径 | 看见最终目标，提前查询当前缺项 |
| C：备用供电区 | 1280–1920 | 两级维修平台、电池 B、线路开关 | 完成简单探索，再返回中央终端 |

路线不是强制流程：玩家可以略过提示牌；所有必要规则仍能通过 HUD 和终端反馈获知。所有关键位置均可步行或一次普通跳跃抵达，不需要隐藏操作。

| `tll_terminal_01` | 灯塔终端 | (960,304) | 中央地面，最终操作位置 |
| `step_c_01` | 第一层台阶 | 上表面 Y=272，X 约 1344–1432 | 与主地面高差 32 |

### 5.3 跳跃与可达性

以下为首轮手感参数，必须经过实际 Godot 游玩调整并记录，不是上游资产固有参数。

| 参数 | 初值 |
| --- | --- |
| 水平速度 | 160 逻辑像素 / 秒 |
| 重力 | 1000 逻辑像素 / 秒² |
| 起跳速度 | -400 逻辑像素 / 秒 |
| 理论最大起跳高度 | 80 逻辑像素，按 `v²/(2g)` 估算 |
| 理论同高度腾空时间 | 0.8 秒 |
| 理论同高度最大水平距离 | 128 逻辑像素；不能直接当作关卡允许极限 |
| 关卡允许的单次台阶高差 | 不超过 40 逻辑像素 |
| 必跳水平间隙 | 不超过 72 逻辑像素，优先避免深坑 |
| 初始玩家碰撞体 | 约宽 28、高 72；脚底对齐原点 |

不加入奔跑加速、惯性滑行和空中连跳。跳跃缓冲或离地宽限可作为后续小幅手感调整，若采用需单独记录参数与测试，不默认为首版已有功能。

### 5.4 镜头、碰撞与遮挡

- 镜头横向跟随玩家并限制在地图内，纵向保持稳定；不靠镜头大幅晃动制造氛围。
- 主地面、台阶使用明确实体碰撞；装饰物不阻挡玩家。
- 碰撞层初始分配：世界层 1，玩家层 2；交互 detection mask 必须检测玩家层 2。此处指层编号，序列化位掩码由程序正确转换。
- 玩家物理节点加入 `interaction_actor`；只有普通 Node2D 加 group 不足以产生感知重叠。
- 角色挂在导出场景 `ActorSlot` 下，相对 Z 保持 0。遮挡以导出顺序为准，不另写一套全局排序。
- 关键交互提示不得被前景、角色或灯光遮住；通过形状、文字和图标表达状态，不只靠颜色。
- 地图替换必须保持原点与碰撞坐标，或提供明确的新旧坐标映射；不通过临时移动玩家来掩盖错位。

## 6. 交互物设计与内容

### 6.1 定义与实例

本版共四种物件定义、五个实例。电池共用定义，两个实例独立记忆。

| 定义 ID | 实例设计 ID | 现有行为 | 触发 / 初态 / 收尾 |

### 6.2 通用配置

- `activation.mode = proximity_press`，`activation.action = workbench_interact`，按键 E。
- `memory.scope = instance`；同关每实例身份唯一。
- 提示牌、开关和终端的感知范围初值：宽 96、高 112，中心向上偏移 48。电池单独采用约宽 64、高 40、中心向上偏移 48 的范围，避免站在下层就隔着平台拾取上层电池；以实际碰撞体触达测试为准。
- 电池 / 终端 / 开关不设置额外阻挡角色的实体碰撞；地面承重由地图负责。
- 单次反馈应短，不采用等待结束的循环动画。
- 冷却建议 0.2 秒；拾取完成标记比冷却更优先。
- 文本显示期间由游戏输入适配层锁定移动和跳跃；工作台通用交互运行时不会自动完成这项游戏控制。

## 7. 美术、动画与声音规格

### 7.1 统一视觉方向

主题：雨后港口、旧工业维修设施、克制的科技元素。停电时偏冷，点灯后以暖金色建立对比。画面避免过多发光招牌、杂乱管线和抢眼背景文字。

建议色彩：背景深蓝 `#182634`，结构灰蓝 `#486070`，环境点缀紫 `#746A91`，可交互强调青 `#67D6C5`，恢复照明暖金 `#FFD582`。这些是方向与 UI 初始色值，不要求生成图片逐像素限制于该色板。

角色和交互物轮廓优先于背景细节；背景对比度适当降低。地图必须是清晰侧视、可横向连接的空间，不采用等距视角或透视地面。

### 7.2 角色与动作清单

| 资产设计 ID | 内容 | 生产规格 | 验收重点 |
| --- | --- | --- | --- |
| `ART-CHAR-01` | 维修员原图 | PixelLab，128×128，透明背景，朝右 | 单角色、完整轮廓、装备一致 |
| `ANIM-IDLE-01` | idle | 建议 6–8 帧，8 FPS，循环 | 呼吸轻微，脚底稳定，无闪烁 |
| `ANIM-WALK-01` | walk | 建议 8–12 帧，12 FPS，循环 | 步态清楚，循环接缝自然 |
| `ANIM-JUMP-01` | jump | 建议 6–8 帧，10 FPS，非循环 | 轻收腿，不包含大幅整体纵向位移 |

帧数与 FPS 是美术需求起点。生成工具实际接受的参数须经 presets / schema 发现；不得编造不支持的请求字段。选定候选后，**实际导出帧顺序、FPS、loop、动作别名是工程接入依据**。如与目标有差异，明确接受或回到导出环节调整，不能导入后偷偷重排或改速。

原图 128×128 不代表所有上游动画一定为该尺寸；导入时核对真实 frame cell。优先选取统一画布尺寸的动作。初始视觉目标为角色有效高度约 80–96 逻辑像素；目标脚底锚点约为 128 画布的 (64,112)，最终采用经审核的真实锚点并记录。

动作映射：静止地面 → idle，移动地面 → walk，上升 / 下落 → jump。跳跃非循环动画结束后保持末帧，落地切回 idle / walk；再次起跳必须作为新动作重新播放。物理腾空由角色控制器负责，动画帧不决定角色高度。

每个动作分别审批并导出 Godot SpriteFrames 包，再合并为同一角色资源。交付包含实际帧图 / 图集、SpriteFrames、预览、导出元数据及来源记录。仅 JSON 或 GIF 不算游戏资产交付。

### 7.3 场景与物件资产清单

| 资产设计 ID | 内容 | 最低交付 | 来源与限制 |
| --- | --- | --- | --- |
| `MAP-01` | 港口灯塔连续地图 | 可编辑源、Godot 导出、碰撞与图层 | 人工使用地图工具；原图可用混元 Image 3.0 |
| `PROP-NOTICE-01` | 提示牌 | 约 48×64 透明 PNG | 人工像素绘制或合法可复用素材 |
| `PROP-CELL-01` | 电池 | 约 24×32 透明 PNG | 两实例共用，不需生成两个图案 |
| `PROP-SWITCH-01` | 线路开关 | 约 48×64 的关 / 开两态 PNG | 尺寸与锚点一致；图形和颜色同时变化 |
| `PROP-TERMINAL-01` | 终端 | 约 64×64 透明 PNG | 首版静态即可，状态灯可由局部表现层控制 |
| `FX-BEACON-01` | 光束、灯芯与环境变化 | 与地图对齐的独立演出层 | Godot 局部表现或人工资源，不烘焙进唯一底图 |

交互物编辑器负责配置行为及打包，**不会自动生成道具图片或音效**。角色原图能力面向角色，不能直接假定它同时提供已验证的道具生产接口。

地图不要求模型一次生成完整目标尺寸。人工先确定侧视风格，再生成中心图、扩展、清理、标注碰撞和组装。具体模型输出与地图工具尺寸约束以届时实际界面为准。

### 7.4 声音与点灯表现

| 资产 ID | 内容 | 优先级与要求 |
| --- | --- | --- |
| `SFX-PICKUP-01` | 电池拾取短音 | 必需，成功后一次，无尖锐峰值 |
| `SFX-SWITCH-01` | 开关机械声 | 必需，只在成功切换后播放 |
| `SFX-LIGHT-01` | 灯塔启动 / 恢复短音 | 必需，与点灯演出开始对应 |
| `AMB-01` | 风或海港环境循环 | 可选，低音量，可静音 |

音频采用已获授权或团队制作的文件，记录来源。不把音效生产归因于当前工作台不存在的音频生成能力。

点灯演出目标 2.8 秒：0–0.4 秒终端状态变化，0.4–1.6 秒灯芯与光束渐亮，1.6–2.8 秒环境暖色恢复并显示胜利标题。不要求重绘整张亮灯地图；一张底图加独立效果层即可。

音频缺失或播放失败不得阻塞胜利；游戏状态由本关流程控制，不能等一个永远不来的声音或循环动画完成事件。

## 8. 工程架构与资产管线对接

### 8.1 采用与不采用的 CopyWorms 方法

本案复用其实际工程方法：角色控制与视觉资源分离、Resource 配置、关卡 / UI Builder、明确的状态所有者、输入锁归属、事件解绑和关卡生命周期。下面列出的源路径用于实施时复核，不表示已经把源码复制到新项目。

| 参考来源 | 本 Demo 的决定 | 实施前必须核对 |
| --- | --- | --- |
| `PlayerModule/Formal/PlayerBase.gd` 及具体角色 | 按其输入、物理、状态到动画的分工实现一个无战斗维修员控制器 | 不直接裁剪原类后宣称可独立使用；检查场景、配置、输入与全局依赖 |
| `Player_Warrior` 的 `Sprite` 与动画切换方法 | 保留 `Sprite` 节点语义、朝向和只在动作变化时切换的规则 | 原始脚底偏移、图集、帧长；不继承 Cyber 冲刺 / 蓄力专用帧逻辑 |
| `DataConfig/` 的 Resource 配置方式 | 本关新增 `DemoConfig` 与 `PlayerConfig` | 默认值必须被实际消费者读取，不能出现第二套硬编码 |
| 关卡 SceneBuilder / UI Builder | 新增本关 Builder，负责导出场景、玩家、UI 与信号组装 | 单一入口和节点所有权；不让通用物件回调具体关卡路径 |
| `EventBus.gd` 的事件与生命周期约定 | 本单关优先使用关卡局部信号连接，保留明确生产者、消费者和解绑 | 若改为直接复用 EventBus，应另审源码、载荷、owner 生命周期，不增加第二条重复业务通道 |
| `InputManager` 的 owner / token 输入锁方式 | 做局部适配，区分交互、暂停、演出持有者 | 每个持有者只释放自己的锁；退出关卡清理本关持有者 |
| MainEntry 容器式关卡承载 | 采用 `GameRoot → LevelSlot → LevelRoot` 一种承载方式 | 不同时移植 whole-tree 转场管理器 |
| 现有交互物运行时 | 独立 Demo 使用 `generic` 导出与现有信号 | `copyworms` profile 依赖原游戏管理器，不因方法来自 CopyWorms 就自动选它 |
| 当前 Frame Ronin / 场景导出 | 使用当前完整导出包，保留资源路径、碰撞、ActorSlot 与共享 runtime | 不按旧 Pixelwork streaming 包处理；不移植旧插件和运行时门控 |

原则：在实际目标工程创建后，补充 `source-to-target.md`，记录直接复用、适配重写、仅参考方法和未采用四种情况。需要搬运的源码必须核对实际提交、依赖与许可；本案不承诺整段源码可无依赖移植。

### 8.4 现有信号与新增接口

现有信号在 `features/interactable-editor/godot-templates/` 中已核对。context 包含 `definitionId`、`instanceId`、`source`、`kind`、`result`；`result` 包含 `completed`、`toggleState`、`sequenceIndex`、`successCount`。

| 现有来源 | 使用方式 | 本关处理 |
| --- | --- | --- |
| 电池 `picked_up(context)` | 只消费这个业务成功信号 | 校验 kind、白名单和实例映射；调用 `register_cell` |
| 开关 `toggled(context)` | 读取 `result.toggleState` | 调用 `set_line_enabled`，再由状态通知 UI |
| 终端 `interaction_finished(context)` | 代表一次终端操作成功提交 | 延迟到当前交互释放后调用 `request_start` |
| 物件 `interaction_cancelled(context)` | 记录取消或恢复 UI | 不增加电池、不切线路、不通关 |
| Runtime `busy_changed(busy)` | 管理交互持有的输入锁 | 只释放交互自己的锁，不解除暂停 / 演出锁 |

**提交顺序要求：** 当前运行时先发物件成功信号，再释放当前交互。Bridge 在绑定时捕获本局 run_id；context.source 是运行中的节点引用，不直接写入资产清单或 JSON 交接记录。因此，收到终端成功信号后不能立即在同一调用栈中开启另一个交互或卸载关卡。使用延迟处理并检查 run_id、节点有效性和阶段；确保演出锁与交互锁交接正确。

以下为本 Demo 新增的语义接口，不是现有 MCP API：

| 接口 / 事件 | 输入或载荷 | 约束 |
| --- | --- | --- |
| `register_cell(instance_id, run_id)` | 电池真实实例身份、本局 ID | 只在未暂停的 PLAYING 受理；非当前局、非白名单、重复实例均不得改变数量 |
| `set_line_enabled(enabled, run_id)` | 当前真实开关值、本局 ID | Bridge 只接受已绑定的线路实例；只在未暂停的 PLAYING 更新，相同值幂等，不自行反转 |
| `request_start(run_id)` | 当前局 ID | 当前局且未暂停的 PLAYING 才判定；返回 `STARTED`、`MISSING_CELLS`、`LINE_OFF`、`MISSING_BOTH` 或 `IGNORED` |
| `state_changed(snapshot)` | phase、收集量、需求、线路、当前局 ID | UI 只读取快照，不修改内部集合 |
| `phase_changed(phase, run_id)` | LIGHTING / WON 等 | 表现层只对当前局响应 |
| `presentation_finished(run_id)` | 当前演出所属局 | 只在 LIGHTING 且匹配当前局时进入 WON |

不同时监听 `picked_up` 与 `interaction_finished` 来给同一块电池加两次分。`interaction_completed` 是物件最终完成，不是游戏胜利信号。序列帧 QA 关键帧索引也不是本游戏的任务触发器。

### 8.5 文本绑定与配置修改

`DemoConfig` 提供规则数值及模板文本。初始化时，TextBinder 校验所有模板并把初始文本注入本局独立的物件配置副本，再允许物件交互；不得修改共享源导出文件或让多个实例意外共用可变配置。

动态 HUD 和终端错误文本使用同一份规则数据。把 `required_cells` 从 2 改为 1 时，应自然影响提示牌、HUD 分母、缺项反馈和启动判定，不能分别修改四处常量。

初版要求**保存配置后停止并重新运行游戏**；不承诺运行中热更新或刷新已缓存的磁盘资源。游戏内“重新开始”用于清空局内状态，继续使用本次启动时加载的配置。演示修改流程为：保存配置 → 停止并重新运行游戏 → 验证一块电池即可满足数量条件且仍需接通线路。

### 8.6 SpriteFrames 接入合同

1. 从资产目录定位真实候选，记录 job、candidate、动作别名、图集与源帧哈希；名称只是显示信息。
2. 优先消费实际存在的 Godot 导出包。每包一个动作，保留包内命名空间和引用。
3. 以现有合并辅助方法生成新的角色总 SpriteFrames；只修改选中动作，保留其他动作；不覆盖来源资源。
4. 把合并资源接入 `Player_Maintainer` 的 `Sprite`。保持唯一视觉节点，不同时加载包的示例角色场景。
5. 只在目标动画变化时切换；再次起跳通过新动作发生标记重播 jump，不在每个物理帧重置播放位置。
6. 只翻转 `Sprite.flip_h`，不镜像物理节点、碰撞体和世界坐标。
7. 脚底偏移、FPS、loop、帧序和透明区域必须实机核对。禁止按文件名字典序猜帧序，也不假定图集每个格子都有效。
8. 不把 animation_finished 作为落地判定；落地仍由物理状态决定。

### 8.7 地图与完整场景接入合同

1. 本项目采用当前手工组装的完整场景 Godot 包，另保存源包。记录实际 exportId、sceneRevision 和入口路径。
2. 新导出先解压到新的暂存目录，核对 ZIP 内容、路径和共享 runtime，再纳入目标工程。
3. 保留 `scenes/<scene-id>/scene.tscn`、地图资源与碰撞及共享 `addons/workbench_interaction/runtime/v1/`；多个包不得互相覆盖不同版本的运行时。
4. 用 Builder 包装生成场景，将人物挂在 ActorSlot，保持排序和坐标。关卡脚本、UI 和演出节点放在生成资源外层。
5. 替换地图或物件后，人工在场景工具应用替换并重新导出；工程人员重新核对真实节点绑定、ID、位置与碰撞。
6. 不能只复制背景 PNG，也不能把完整场景包当作带 project.godot 的完整游戏。
7. 地图 / 场景浏览器草稿必须另存源包；资产目录能看到导出，不代表能恢复任意未导出的浏览器编辑。

### 8.8 输入、UI 与生命周期

- GameRoot 只使用容器式关卡承载。重开先使旧 run_id 失效，停止接收旧业务事件，再释放连接和锁，最后建立新关卡。
- UI 建议层级：HUD 10、通用交互对话 50、暂停 80、结算 90。实施时核对实际导出 runtime 的层级，不覆盖其结构来凑画面。
- 交互、暂停和演出各自持有输入锁；交互结束不得提前恢复演出期间的移动。
- E / Enter 对话推进必须消费输入，关闭对话的按键不能在同帧又触发一次物件操作。
- Esc 在对话 busy 时不新开暂停菜单；由 E / Enter / 对话按钮完成当前交互。点灯演出很短且不能暂停，窗口关闭仍正常响应。
- 暂停应停止角色、局内演出计时和环境动画的相应进程；暂停 UI 保持可操作。正常情况下 LIGHTING 不允许进入暂停。
- 节点退出时断开业务连接并取消其计时 / 延迟回调。新局拒绝所有旧 run_id 的回调，不以“通常不会发生”为依据省略。

## 9. Forge / WorkBuddy 制作流程

### 9.1 能力与负责人边界

| 环节 | 现有入口 | 执行者 | 产物与完成证据 |
| --- | --- | --- | --- |
| 理解任务、确认范围 | 对话与工程 Skill | 制作负责人 + WorkBuddy | 已认领的工作包与资产清单 |
| 原图与动作生产 | reference-art / sprite-generator | 获授权的 Agent 操作，人工或有效视觉审核 | 指定候选、实际帧图和 Godot 包 |
| 地图原图、扩展、清理、碰撞 | 地图前端 | 人工 | 可编辑地图源、Godot 包、碰撞检查 |
| 交互物配置与导出 | interactable-editor MCP / 前端 | Agent 配置，人工检查视觉与交互 | 真实素材、源 JSON、Godot 包 |
| 地图与物件摆放、遮挡 | scene-composer 前端 | 人工 | 场景源包、Godot 包与导出版本 |
| 导入、组装、玩法脚本、打包 | 工程 Skill + Godot 工程 | 程序 / WorkBuddy | 源码、实际引擎运行与成品 |
| 最终验收 | 实际游戏与制作证据 | 测试 + 制作负责人 | 用例结果、录像、缺陷关闭记录 |

地图及场景组装保持人工边界。Agent 可以写出布局和参数建议、读取已保存导出，但不得用 MCP、CLI、HTTP 或浏览器自动化替人工生成和拼接地图。

### 9.2 原图与序列帧生产步骤

1. 先检查已有资产；本案尚未选择实际角色候选，不能把诊断素材或旧角色直接登记为新角色成品。
2. 在额度、模型配置和生成授权明确后，生成 / 选择维修员原图。
3. 将选定原图 transfer 为角色预设；transfer 本身不生成动作。
4. 从实际 presets 选择 idle、walk、jump 对应动作，逐项生成并跟踪原任务。
5. 执行检查与安全检查，观看真实连续动作，记录审核依据；通过后导出。
6. 领取实际存在的 Godot 包，记录每个动作的候选和来源。检查成功、任务 completed、图片下载成功分别不是整个动作交付的同义词。

外部请求超时先查已有任务，不重新 run 碰运气。未批准候选不进入最终美术锁定；灰盒期间可用明确标记的临时视觉，不能出现在最终交付中冒充生成资产。

### 9.3 资产身份、版本与交接

`ART-...`、`MAP-...` 是设计编号；Forge 返回的 assetId、jobId、candidateIndex、exportId 才是来源身份。二者通过交接表对应，不得互相替代。

每次资产交付至少填写：

| 字段 | 要求 |
| --- | --- |
| 设计 ID / 版本 | 如 `ANIM-WALK-01 / v01`，稳定命名 |
| 实际来源 | 工具、provider（如适用）、资产 / 任务 / 候选 / 导出身份 |
| 源文件 | 可编辑源或原导出包的真实相对路径 |
| 校验 | 实际 SHA-256，不能填说明性字符串伪装为校验值 |
| 规格 | 尺寸、透明背景、锚点、帧序、FPS、loop、变换等适用字段 |
| 审核 | 审核人、日期、发现与处理；未审核明确写未审核 |
| 引擎引用 | 最终资源路径及引用场景 |
| 授权 / 来源说明 | 自制、模型生成或第三方复用依据 |

最终 `asset-lock.json` 记录当前交付所使用的确定版本。文件名相同不代表内容相同，重新导出后重新核对 hash 和候选身份。归档生产历史不改变锁定资产的身份。

### 9.4 生成预算与重试规则

预算由制作负责人在实际生产前确定，当前未获指定金额或次数，不在本案虚构额度。按“角色原图、三个动作、地图原图 / 扩图”分别登记预计请求次数、实际请求和选用结果。

超出已同意的生成范围、预算，或需要更换模型时，先给出具体原因与预期收益。不得为了演示重新生成已经可用的素材，也不得将纯计划或沟通登记成大量空生产任务。

### 12.3 首次体验与性能观察

- 至少请两位未参与关卡制作的人独立体验，不在旁边逐步指挥。
- 记录发现移动、第一次交互、第一次到终端和通关的时间，以及停滞位置。目标是首次体验约 2–4 分钟；明显超时先改善引导，不直接缩短地图掩盖问题。
- 目标机器与分辨率必须写入记录。初始性能目标是正常游玩接近稳定 60 FPS、无持续明显掉帧；不把开发机一次成功推广为所有设备都能达到。
- 必须检查图片尺寸 / 内存、导入后资源完整性和完整流程。不能仅凭“导出 ZIP 成功”判定游戏完成。

### 12.4 发布阻塞等级

| 等级 | 例子 | 发布处理 |
| --- | --- | --- |
| 阻塞 | 无法启动、无法通关、关键资源缺失、重开死锁 | 必须修复 |
| 严重 | 重复计数、错候选、错误坐标 / 碰撞、规则文字不一致、宣称的制作路径不可复现 | 必须修复 |
| 一般 | 不影响操作的小型视觉 / 排版问题 | 记录后由负责人决定，演示主路径可见问题优先修复 |
| 建议 | 额外美化或非必需玩法 | 不影响 v1.0 发布 |

最终验收需完成所有适用核心用例。变更后按影响重新执行关联用例及一次完整通关，不以早期灰盒记录替代正式版本验收。

## 14. 风险、降级与禁止替代项

| 风险 | 优先处理 | 可接受降级 | 不能采用的替代 |
| --- | --- | --- | --- |
| 外部模型慢或不稳定 | 提前生产、复用已批准候选，查询原任务 | 使用已验收的真实生产资产录屏 | 冒充现场即时生成或反复提交付费任务 |
| 角色动作质量不一致 | 保留统一原图与候选审核，调整少量问题 | 降低装饰细节，保持三个必要动作 | 用静态图冒充动画验收通过 |
| 地图细节杂乱 / 接缝 | 人工清理、降低背景对比度、减少装饰 | 缩短非必要装饰区，保留三功能区与可达性 | 自动绕过地图操作边界 |
| 道具美术缺口 | 采用团队制作的简单像素图 | 静态开关两态、静态终端 | 声称交互物 MCP 已自动生成图片 |
| 点灯表现耗时 | 局部光束、颜色与 UI 反馈 | 减少粒子、取消非必要雾效 | 删掉通关反馈或用视频替代实际效果 |
| 资产导出更新覆盖脚本 | 自定义脚本外置、版本化暂存、差异检查 | 回退到上一已验收资源包 | 直接覆盖整个项目后靠手工补救 |
| 跨人编辑丢失 | 源包交接、单一编辑负责人、真实版本登记 | 暂停并行修改同一场景 | 只依赖浏览器自动保存 |
| 现场网络或 MCP 不可用 | 预演、保留已验收本地包与真实录屏 | 明确转为展示本地成品与录制流程 | 把离线回放说成 MCP 刚执行成功 |
| 时间不足 | 先保核心闭环，移除所有可选项 | 无环境音乐、少装饰、短文案 | 移除重开、来源记录或真实游戏验收 |
