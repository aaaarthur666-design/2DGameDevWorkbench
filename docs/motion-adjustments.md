## 使用流程

在分段确认或“检查与调整”点击“调整部分帧”，进入专注的调整区域；“返回动画检查”回到原片段。默认只需选帧和填写要求。主检查页保留播放与必要确认，专家依据集中在“检查详情”，结构观察、锚点裁切与停止制作位于“高级工具”。恢复入口仅在存在待恢复的绘图请求时出现。

“修改要求”留空时，使用当前范围的专家建议；填写时，以用户原话建立新修改目标，专家建议不能覆盖它。没有可执行建议且要求为空时，需要补充希望尝试的变化。修改要求与专家意见分别留存，不混成无法追溯的旧缺陷说明。

提交前显示理解、绘图和复核上限。一次任务最多一次需求理解、一次 PixelLab 请求，以及两次基础复核或至多五次增强复核；无争议可少一次。现有模型设置用于新修改任务并冻结，凭据仍从保护存储读取。明确选择范围、授权上限后无需再选择内部修复类型。

默认直接按原帧和文字要求修改，不要求涂选，也不显示“只改外观，保留原动作”模式开关。未要求变化的姿势、外观、时机应保留；明确的姿态偏好也可提出。主动勾选“精确限定修改区域（可选）”才显示画笔，由本地合成保护区域外 RGBA。未勾选时没有空间硬锁定，须看实际对比。任何模式都不能因帧数限制把外观修改改成动作重生成。

备选生成后，在同页同步播放原版与备选、逐帧观察、检查完整片段及两侧衔接。分别显示“修改目标”和“其他内容保持”，不能用目标改善抵消新退化。区域编辑还显示区域外像素的实际核验；这只证明保护区没变，不证明改动区域好看。采用前保存视觉与技术报告。用户实际播放并填写简短结论，确认需要接受的提醒后采用；保留原版不会删除备选、未知请求或已产生费用。

需求理解使用与页面一致的从 1 开始的原帧编号；绘图提示只描述所选局部窗口，不把完整动画编号误传成绘图输入槽位。视觉观察先读取备选；后续审查、独立专家与争议复核同时看到受保护的原版作对照，判断修改目标及未要求改变的姿势、外观和两侧衔接。这些对照复用原有调用，不增加复核次数。

进入修改区时收起原播放与采用工具，避免两套操作并列。只有真实备选存在时显示对比和采用选择；理解失败的记录明确标注“未生成备选”。已完成备选自动呈现，旧结果通过“修改记录”查看。完整候选有未处理备选时刷新返回检查页；保留原版后可继续导出。逐帧编辑工作区位于“高级工具”。

## 保证与边界

- 范围绑定作品版本、候选、真实帧哈希、参考图、FPS、循环和计划。未选中帧逐张保持原文件字节；不改帧序、帧数或FPS。
- 可选区域模式同时限制帧范围与逐帧区域。区域只能来自明确授权，不能把结构蒙版或时序观察当作空间修改许可，也不能把一帧坐标直接套到另一姿势。此模式区域外 RGBA 逐像素不变；所有模式未选中帧保留原文件字节。区域内部的效果与接缝仍须判断。
- PixelLab 没有因此获得空间蒙版控制接口：它收到原帧及有边界说明的提示，原始返回完整保留，实际交付用二值区域合成。透明区域内允许删除碎片，区域外的透明度与颜色不变。范围过窄可能留下接缝，模型若移动了整个物体，合成也不保证选区内合理；不会扩大区域修补或自动再次生成。
- 未传 `edit_regions` 是正常的时间窗口编辑路径，不能声称帧内像素锁定。勾选区域模式后，每个选中帧必须有非空、非全图的有效区域；切换来源后旧区域失效。
- 128像素外观编辑目前一次支持2个目标帧；64像素支持2–14个偶数目标帧。运动过渡支持4–16个偶数帧。模型输入中的参考/上下文图片不进入替换结果。
- 起始帧、完整候选中已锁定的分段锚点和跨段范围仍受保护。当前未确认片段若后段尚未提交、末尾未绑定原图或外部目标图，末帧可以包含在用户明确选择中。界面标记“未锁定段尾”；采用并确认本段后，新的真实末帧才成为后段输入。
- 未锁定段尾的外观编辑用受保护的前一帧作额外上下文；过渡生成从该前一帧开始，不把有缺陷的旧末帧当作固定目标。只接纳提供方返回的所选数量，额外输入上下文须核验后排除；范围外 PNG 字节、帧序与 FPS 保持不变。过渡生成可能改变所选帧的姿势，不能承诺仅改变局部像素。
- 单帧、奇数帧或不支持的范围会在付费调用前拒绝，不扩大用户选择、补帧或删帧。128 像素外观编辑一次只能选 2 帧，第 13–16 帧要求保留动作时会在调用模型前拒绝，不偷偷切换生成方法或拆成多次收费请求。只有明确修改动作的需求才适合评估 4–16 偶数帧的过渡生成。
- 当前未锁定片段采用后绑定新帧和已经完成的备选报告，仍需明确确认该片段。完整候选采用后建立同一作品的新版本和新原生作业，原版本、原候选与导出保留。
- 用户要求改变保护范围、整体时长等内容时，意图理解应说明冲突并停止绘图。当前范围没有适合的方案时，不假装完成修改。
- 原版与修改版的完整性评价以本次要求为准；用户要求覆盖冲突的专家建议，后续明确采用的局部修改按顺序覆盖更早的同范围要求。最终整段检查仍保留。

## 费用、失败与恢复

每个修改任务分别保存规划、绘图、视觉调用的请求身份、输入摘要、模型、响应和用量。`work.adjustment_usage` 汇总这个作品历次修改的调用次数；原生任务预算与独立修改预算分别核算，不重复扣除或在弃用后清零。

绘图试做按当前版本、候选和片段（或完整候选）中的实际帧分别计数，每帧最多参与两次修改绘图。13–14 帧的尝试不占用 15–16 帧的次数；部分重叠的选择取所选帧中的最少剩余次数，不能移动边界绕过已经用完的帧。采用后也不清零同一帧的历史次数。未进入绘图的理解失败或需求冲突不占绘图名额，但规划费用和失败记录仍保留；已提交、失败或结果未知的绘图均计数。旧局部修复只占其实际涉及帧的次数，其原有任务总预算和接口限制不变。每次新提交仍需明确授权独立上限，已有待处理/未知备选仍阻止并行新建。重复请求标识只返回原任务，读历史不会续费或重试。

上下文返回 `attempt_scope=selected_frames`、`attempt_limit=2`、逐帧的 `frame_attempts` 和 `legacy_frame_attempts`。Agent 应读取当前选择覆盖的计数，不得用 `tasks.length` 推断额度；任务条数包括理解失败与不同范围的记录。关联已完成的隔离试做也按真实绘图范围计数，不抹除费用。

后台只推进已授权的任务。未知提交或中断的模型调用保留记录并停止，不自动重新生成。GET、刷新、读历史和查询MCP任务不发起新的规划/绘图。原始图片或任务合同变化时，备选保留但不能直接采用到新来源。

新修改任务冻结意图格式版本 4：沿用已验证 TokenHub Kimi 的严格 JSON Schema。明确用户要求存在时，历史专家建议留在记录中，不作为额外修改目标送入理解请求。绘图使用一次完整简短的目标翻译，并为槽位/区域说明预留长度，不重复拼接原话、旧动作或理想收势，不截断。空要求只使用相关具体建议。旧 v1/v2/v3 请求、提示词、身份与冻结摘要不升级。失败不自动重试。

新增区域任务冻结 `spatial_policy=source_pixels_v1`、逐帧来源哈希和稀疏二值区域；Kimi 提示字段长度根据用户原话与保护说明的剩余空间计算，不截断用户要求。新任务另冻结 `comparison_protocol=1`：复用原观察、审查、独立外观/动作意见及至多一次争议复核，在相同调用中分别回答 `change` 与 `preservation`。任一项失败不能被另一项通过抵消；比较项争议也能触发原预算内的第五次复核，不增加额外调用。取消先前疑点仍需人工画面裁决，缺失或无效结论不能变成通过。旧任务缺少此字段时沿用原检查合同。

HTTP 拒绝保存状态码、合规错误码、已识别的参数名与提供方请求编号，不保存或展示原始错误正文、图片、提示词或凭据。HTTP 400 不能直接推断为余额不足或图片丢失；历史记录没有保存具体原因时须保留未知，不自动重试或改用其他模型。

采用前验证图片和报告绑定；阶段采用复用同一份检查结果，不重复请求模型。报告在独立任务账本记录费用，原生阶段保留来源链接。采用后整段组装的检查是不同范围，仍使用原有预算。技术硬错误仍禁止采用；模型不确定不等于自动通过，需实际画面裁决。

## MCP 输入

均属于 `sprite-generator`；先读取当前 capability schema。

1. `get-motion-adjustment`：带 `openWorkId`、`expectedRevision`、`candidateIndex` 读取上下文。指定 `stageIndex` 为当前未锁定片段，省略为完整候选。返回 `adjustmentContext`、可修改范围、当前建议、调用上限和校验过的 `orderedFrames`。这一步不提交模型。
2. `create-motion-adjustment`：带同一身份、`adjustmentToken`、零基闭区间 `adjustmentStart/adjustmentEnd`、可选 `adjustmentRequest`、`generationAuthorized=true`、`adjustmentBudget` 和稳定 `requestKey`。默认可以不传区域；已明确只修外观时可传 `adjustmentPreserveMotion=true`，提前拒绝超出原帧编辑容量的范围。只有用户主动选择空间保护时才提供 `adjustmentRegions`，并同时传 true；每项 `{frame, source_sha256, spans:[{start,length}]}` 绑定实际帧哈希，不能猜坐标。没有区域不等于允许无关改动，也不能声称像素锁定。用户原话放在 `adjustmentRequest`。
3. 用 `workbench_get_task` 跟进同一执行任务；也可用带 `adjustmentId` 的 `get-motion-adjustment` 读取已有修改。返回真实原帧和备选帧路径，按完整顺序播放，不以GIF首帧代替检查。
4. `review-motion-adjustment`：使用来源 `expectedRevision`、`adjustmentId`、`adjustmentToken=preview_token`、`stageDecision=accept|reject`。采用需实际 `reviewNote` 及必要的 `acknowledgeWarnings`。尚无预览的失败/未知请求保留原版时使用 `source_token`。

新协议不改变旧 `repair-motion-stage`、旧方案哈希或旧任务执行语义。界面与 MCP 使用同一后台。一次修改任务归属原作品，不把它另算一件已完成美术资产。完整候选只有明确采用后才形成可导出的衍生版本；不代表已接入游戏工程。

## 维护与验收

核心：`collaboration/adjustments.py`（独立任务、冻结范围、预算与执行）、`adjustment_regions.py`（明确区域、本地回填与 RGBA 核验）、`adjustment_comparison.py`（修改目标与保留内容的独立结论）、`adjustment_review.py`（复用检查）、`adjustment_delivery.py`（采用及衍生版本）。UI 为 `motion-adjustment.tsx` 与按需出现的 `motion-edit-region.tsx`，MCP 清单与 Sprite 适配器共享原生接口。

先运行 `tests/test_motion_adjustments.py`、现有开放动作与专家复核测试、`test:open-motion`、隔离浏览器完整流程，再运行开发指南要求的接口/MCP/Agent/壳层回归、类型检查和构建。Skill更新运行两份 validator。

真实质量验收另需明确额度，记录基线与备选的全部实际帧、修改范围外哈希、真实调用与弃用结果。分别验证用户指定方向、采用专家建议、保留满意原版，以及备选更差时的退出路径。模拟接口与模型报告均不能证明真实效果提升。

2026-10-27 失败案例：128 像素的第 13–16 帧原本只要求修外观，却被帧数限制导向过渡重生成，并重新引入规划收势，造成姿态、人物轮廓和碎片退化。实际用了 1 次理解、1 次绘图、5 次复核；即使模型部分维度通过，用户实际对比判定失败，备选已拒绝且原版保留。版本 3 的免费回归只证明这类错误路由受到约束，不证明修复美术质量已通过；不得沿用该轮授权追加生成。

同日新增区域保护后的单组实测另获授权，只编辑第 13–14 帧，调用仍为 1 次理解、1 次 PixelLab、5 次视觉复核，无重试、无采用。区域外 RGBA 零改动，其余 14 帧文件字节不变，人物姿态与外观保持，十字碎裂与散落亮点减少；但两帧的刀刃投影长度与曲直仍有差异。模型对目标改善给出通过，人工实际查看不接受其“长度形状一致”的结论。因此仅记工程保护通过和局部视觉改善，不记完整美术通过，也不推断组合泛化能力。

本地维护可用 `adjustment_import.register_saved_alternative` 关联已完成的隔离备选。调用者必须指定原作品、版本、候选、片段和来源 token；函数验证冻结输入、原图、全部 PNG、复核证据和请求身份，原子复制并保存关联来源。旧费用仍计入范围试做上限，无新调用、无采用，也没有新增 MCP 操作。不得把不同来源的成功样例关联为当前任务备选。

2026-10-27 默认文字路径回归：另获明确授权，在两个隔离副本上各执行一次，均不涂选。旧成功样例第 8–9 帧（减弱拖尾）保持原角色、用户原话、原帧与种子，实际大片白色拖尾减弱，原运动阶段未被重做；未选 16 帧字节不变。武器样例第 13–14 帧清除了十字碎片、人物主体保留，但两帧刀刃角度变化及接回未改第 15 帧的跳变仍在，人工未判完整通过，即使模型目标结论通过。合计 2 次理解、2 次编辑、9 次视觉复核，没有重试或采用。前者支持恢复普通原帧编辑的方向，不证明普遍精修可靠；后者保留为边界失败材料。新旧三列逐帧与同步播放保存在本地验收目录，完整 Python 639 通过、2 跳过，浏览器与接口回归通过。
