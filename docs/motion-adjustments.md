# 用户选帧修改与备选版本

2026-10-26。此功能用于开放动作作品的明确调整，也接受个人偏好；不要求专家先判定原动画有错。只读查看、选帧和填写要求不创建任务。用户明确点击“生成一个备选”或授权 Agent 提交后，才保存独立修改任务并使用额度。

## 使用流程

在分段确认或“检查与调整”中展开“调整部分帧”。拖动帧缩略图选择连续范围，或填写起止帧。保留帧和锚点明确标出；未选中帧不参与替换。专家建议只显示与选择有关的部分，详细依据按需展开。

“修改要求”留空时，使用当前范围的专家建议；填写时，以用户原话建立新修改目标，专家建议不能覆盖它。没有可执行建议且要求为空时，需要补充希望尝试的变化。修改要求与专家意见分别留存，不混成无法追溯的旧缺陷说明。

提交前显示理解、绘图和复核上限。一次任务最多一次需求理解、一次 PixelLab 请求，以及两次基础复核或至多五次增强复核；无争议可少一次。现有模型设置用于新修改任务并冻结，凭据仍从保护存储读取。明确选择范围、授权上限后无需再选择内部修复类型。

备选生成后，在同页同步播放原版与备选、逐帧观察、检查完整片段及两侧衔接。采用前保存视觉与技术报告。用户实际播放并填写简短结论，确认需要接受的提醒后采用；保留原版不会删除备选、未知请求或已产生费用。

需求理解使用与页面一致的从 1 开始的原帧编号；绘图提示只描述所选局部窗口，不把完整动画编号误传成绘图输入槽位。视觉观察先读取备选；后续审查、独立专家与争议复核同时看到受保护的原版作对照，判断修改目标及未要求改变的姿势、外观和两侧衔接。这些对照复用原有调用，不增加复核次数。

进入修改区时收起原采用表单，避免两套操作并列。完整候选有未处理修改任务时，刷新返回检查页；保留已采用的原版后可继续导出。旧逐帧编辑入口位于“其他调整工具”；已有旧修复记录仍可查看和处理。

## 保证与边界

- 范围绑定作品版本、候选、真实帧哈希、参考图、FPS、循环和计划。未选中帧逐张保持原文件字节；不改帧序、帧数或FPS。
- 这是时间窗口修改，不是空间蒙版。选中帧内部未提及的角色部分只能约束模型保持，不能保证像素完全不变。
- 128像素外观编辑目前一次支持2个目标帧；64像素支持2–14个偶数目标帧。运动过渡支持4–16个偶数帧。模型输入中的参考/上下文图片不进入替换结果。
- 首末帧、分段锚点、跨段范围不能作为普通窗口提交。单帧或不支持的范围会在付费调用前拒绝，不扩大用户选择、补帧或删帧。
- 当前未锁定片段采用后绑定新帧和已经完成的备选报告，仍需明确确认该片段。完整候选采用后建立同一作品的新版本和新原生作业，原版本、原候选与导出保留。
- 用户要求改变保护范围、整体时长等内容时，意图理解应说明冲突并停止绘图。当前范围没有适合的方案时，不假装完成修改。
- 原版与修改版的完整性评价以本次要求为准；用户要求覆盖冲突的专家建议，后续明确采用的局部修改按顺序覆盖更早的同范围要求。最终整段检查仍保留。

## 费用、失败与恢复

每个修改任务分别保存规划、绘图、视觉调用的请求身份、输入摘要、模型、响应和用量。`work.adjustment_usage` 汇总这个作品历次修改的调用次数；原生任务预算与独立修改预算分别核算，不重复扣除或在弃用后清零。

每个版本/候选/片段最多两次试做，片段范围计入旧局部修复次数。完整候选的独立试做同样最多两次。重复提交同一请求标识返回原任务；同标识不同输入拒绝。另建任务不代表前次费用被退还或删除。

后台只推进已授权的任务。未知提交或中断的模型调用保留记录并停止，不自动重新生成。GET、刷新、读历史和查询MCP任务不发起新的规划/绘图。原始图片或任务合同变化时，备选保留但不能直接采用到新来源。

采用前验证图片和报告绑定；阶段采用复用同一份检查结果，不重复请求模型。报告在独立任务账本记录费用，原生阶段保留来源链接。采用后整段组装的检查是不同范围，仍使用原有预算。技术硬错误仍禁止采用；模型不确定不等于自动通过，需实际画面裁决。

## MCP 输入

均属于 `sprite-generator`；先读取当前 capability schema。

1. `get-motion-adjustment`：带 `openWorkId`、`expectedRevision`、`candidateIndex` 读取上下文。指定 `stageIndex` 为当前未锁定片段，省略为完整候选。返回 `adjustmentContext`、可修改范围、当前建议、调用上限和校验过的 `orderedFrames`。这一步不提交模型。
2. `create-motion-adjustment`：带同一身份、`adjustmentToken=adjustmentContext.token`、零基闭区间 `adjustmentStart/adjustmentEnd`、可选 `adjustmentRequest`、`generationAuthorized=true`、`adjustmentBudget` 和稳定 `requestKey`。用户原话放在 `adjustmentRequest`，不能用视觉结论字段 `reviewNote` 代替。
3. 用 `workbench_get_task` 跟进同一执行任务；也可用带 `adjustmentId` 的 `get-motion-adjustment` 读取已有修改。返回真实原帧和备选帧路径，按完整顺序播放，不以GIF首帧代替检查。
4. `review-motion-adjustment`：使用来源 `expectedRevision`、`adjustmentId`、`adjustmentToken=preview_token`、`stageDecision=accept|reject`。采用需实际 `reviewNote` 及必要的 `acknowledgeWarnings`。尚无预览的失败/未知请求保留原版时使用 `source_token`。

新协议不改变旧 `repair-motion-stage`、旧方案哈希或旧任务执行语义。界面与 MCP 使用同一后台。一次修改任务归属原作品，不把它另算一件已完成美术资产。完整候选只有明确采用后才形成可导出的衍生版本；不代表已接入游戏工程。

## 维护与验收

核心：`collaboration/adjustments.py`（独立任务、冻结范围、预算与执行）、`adjustment_review.py`（复用检查）、`adjustment_delivery.py`（采用及衍生版本）。UI为 `motion-adjustment.tsx`，MCP清单与Sprite适配器共享原生接口。

先运行 `tests/test_motion_adjustments.py`、现有开放动作与专家复核测试、`test:open-motion`、隔离浏览器完整流程，再运行开发指南要求的接口/MCP/Agent/壳层回归、类型检查和构建。Skill更新运行两份 validator。

真实质量验收另需明确额度，记录基线与备选的全部实际帧、修改范围外哈希、真实调用与弃用结果。分别验证用户指定方向、采用专家建议、保留满意原版，以及备选更差时的退出路径。模拟接口与模型报告均不能证明真实效果提升。
